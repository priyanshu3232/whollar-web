Opening a cohort

One row in one table puts a campaign in front of households and in front of partners. This is what that row has to say, in what order to write it, and why the newest cohort is the featured one.

Who this is forThe operator with ZCQL write access in the Catalyst console.
Companion filesscripts/cohort.mjs, docs/COHORT_RUNBOOK.md, create-tables.md sections 16, 18, 20.
Standing ruleThe tools print statements. They never write. Every write is yours, pasted deliberately.

Part one

Three rules that decide everything else

Nothing in the command list makes sense until these are true in your head. Each one is a single column doing a single job.

Rule 1. A cohort takes joins or bids, never both

kind is one column. Joining is open on planned, waitlist and forming. Bidding is open on auction. A sealed auction runs against a locked household count, so the moment bidding opens, joining is over, permanently. There is no join path back.

Rule 2. The server owns the stage. The browser only renders it

Stage is derived on every read from the seven calendar dates, never stored and never computed in a browser. A visitor's clock running four minutes fast must not be able to disagree with the server about whether a sealed window is open. Labels come down the wire; countdowns offset from the serverTime in the same response.

Rule 3. Featured is not a column. It is the lowest sort_order

The catalog is sorted ascending, so the smallest sort_order is the first card. To make the newest cohort featured you count down, which is also why adding a cohort never has to rewrite the ones already there.

Every column in the row, and what it decides

Eleven columns plus a seven date calendar. Step 3 writes all of them in one statement, so this is the reference for what you are actually saying, not a second thing to type.

Datetimes are UTC, in Catalyst's own format

'YYYY-MM-DD HH:MM:SS', which is neither ISO-8601 nor your local time. The generator prints them correctly. Typing one by hand is how a cohort ends up closing at 5pm in a timezone nobody lives in.

What actually opens a bid window

Four conditions, all four checked on the server on every bid write. Three of them are rows you control. The fourth is the clock.

ConditionWhere it livesIf it is wrong
kind = 'auction'campaignsThe desk shows the cohort with no bid button.
bidding_open = truecampaignsSame. Entering auction never opens bidding on its own, by design.
bidding_closes_at aheadcampaignsEvery bid is refused while the row still reads open. Dates may close a window and may never open one.
bidding_enabledsite_configGlobal kill switch. Absent means on.

Two failures that are completely silent

A region no partner can declare. The region name is the entire join between a cohort and a partner, matched by slug, server side. Name a cohort for a place outside the 37 declarable regions and it renders on both dashboards, takes joins, runs its clock down, and takes no bids. Nothing is logged. It reads as a market that did not bite.

A missing table. campaigns and campaign_members fall back to a code catalog and seed counts when they cannot be read, so their absence looks like a working site. provider_terms is the opposite: it fails closed, and while it is missing no bid can be placed at all.

Part two

Why the newest cohort is the featured one

You asked for cohort B, created after A, to be featured, with A sliding to position 1. That works, and it takes exactly one number.

The three things that outrank your number

"Featured" is decided by the member dashboard in this order. Your sort_order is the last tiebreak, not the first authority.

OrderWhat winsConsequence for you
1stThe member's own cohort A household that has joined something always sees theirs featured. Nothing you write changes that, and it should not.
2ndkind, in lifecycle order A forming cohort sits above every auction one whatever its number. So "newest featured" holds only among cohorts of the same kind. Households read what they can join before what they cannot.
3rdsort_order, ascending Your ladder. It orders cohorts inside one kind.

The one thing to accept before you start

A cohort that is open to bid is an auction, and an auction is not joinable. So the featured card will read Sealed bidding and will carry no join button. That is rule 1 doing its job, not a bug.

If the featured card must be joinable, create at forming instead, collect the joins, and open the auction afterwards. That is the long path in docs/COHORT_RUNBOOK.md. You cannot have both at once on one cohort.

Part three

The sequence, start to finish

Seven steps. The terminal steps print statements and write nothing. The zcql steps are what you paste into Catalyst console, Data Store, ZCQL, environment Development.

Fill these in once

PlaceholderWhat it isNot negotiable
<ID>the slug, campaign_id 3 to 64 characters of a-z, 0-9, hyphen. Permanent: both dashboards key on it and every bid receipt is built from it. Never appears on screen.
<REGION>the region name Must be one of the 37. This is the whole join to a partner.
<REGION_SLUG>region, lowercased, runs of non-alphanumerics to one hyphen Only used to build coverage_key.
<SORT>sort_order Lower is featured. Start at 100, take one off per cohort.
<DAYS>days until bids close 1 to 6 opens the window now. 8 or more writes bidding_open = false.
<ORG_ID>the partner org that should see it From SELECT org_id, legal_name FROM provider_orgs;
1zcql

Prove the tables exist zcql

Each of these must return without an error. Zero rows is a pass. Run this once per environment, not once per cohort.

SELECT ROWID FROM campaigns LIMIT 1;
SELECT announce_at, bidding_opens_at, bidding_closes_at, offers_at,
       decision_at, switch_window_at, reconcile_at FROM campaigns LIMIT 1;
SELECT ROWID FROM campaign_members LIMIT 1;
SELECT coverage_key, org_id, region, status FROM provider_coverage LIMIT 1;
SELECT acceptance_key, org_id, doc_type, doc_version FROM provider_terms LIMIT 1;

Anything that errors gets built from create-tables.md, sections 16, 18 and 20. An existence check that needs no console at all: cd catalyst-backend && catalyst ds:export --table campaigns --page 1

2terminal

Check the name can be bid on terminal

This is the check ZCQL cannot do for you, and the one that has already produced live cohorts nobody could bid on.

node scripts/cohort.mjs regions

<REGION> must be in that list. <ID> is usually its slug but does not have to be: region is what renders and what coverage matches, <ID> is only the key.

3both

Create it, open to bid, in one statement terminal zcql

One INSERT is the entire creation, for both dashboards at once. There is no second row to write for the consumer side.

node scripts/cohort.mjs seed <ID> --regions "<REGION>" --first <DAYS> --sort <SORT>

Paste the one INSERT it prints. It carries kind = 'auction', bidding_open = true and all seven calendar dates:

INSERT INTO campaigns (campaign_id, region, kind, seed_members, seed_households,
  bidding_open, sort_order, updated_by, updated_at, announce_at, bidding_opens_at,
  bidding_closes_at, offers_at, decision_at, switch_window_at, reconcile_at)
VALUES ('<ID>', '<REGION>', 'auction', 0, 0, true, <SORT>, 'manual', '<now>',
  /* the seven dates, spaced around the close: */
  '<close -10d>', '<close -7d>', '<close>', '<close +2d>',
  '<close +9d>', '<close +12d>', '<close +26d>');

--regions can be dropped when <ID> title-cases into <REGION> exactly. Seeds stay at 0 deliberately: a seed count is added to real joins on both surfaces, so a non-zero seed is padding a partner will eventually bid against.

3b

The same thing on a test rail, in minutes terminal zcql

For a test case rather than a launch. --minutes replaces --first and dates the whole batch from now, so one statement lands a cohort that is featured on the consumer side and biddable on the desk straight away.

node scripts/cohort.mjs seed <ID> --minutes 5 --sort <SORT>
ColumnLands atWhy there
announce_at-2 intervalsjoining has already shut
bidding_opens_at-1 intervalbehind you deliberately. The desk draws its button on stage open or closing, and neither is reachable until this date has passed
bidding_closes_at+1 intervalso the bid window is two intervals wide: ten minutes at --minutes 5, twenty at 10
offers_at+2the rest runs one stage per interval
decision_at+3and this one is read first by the stage engine, so it ends the run
switch_window_at+4
reconcile_at+5the whole rail finishes here, 25 minutes out at --minutes 5

2 is the floor, and 1 is refused rather than quietly unwatchable: the catalog is memoized for 60 seconds. Every cohort in a batch runs the same rail, so a row of cards stays comparable. --minutes and --first cannot be combined. And note the member rail only advances on its own for a member who has joined that cohort, which an auction cannot be, so a full rail test means creating at forming, joining, then moving to auction.

4both

Give it coverage, or it reaches nobody terminal zcql

A campaigns row alone is on no partner's desk. It reaches every partner whose declared coverage matches the region and is active, and nobody else. One row per org, per region.

node scripts/cohort.mjs coverage <ORG_ID> --region "<REGION>"

That prints the INSERT, and the UPDATE to use when the row already exists. New coverage lands verifying, which greys the desk row with "Verifies with <REGION> coverage". Move it on:

UPDATE provider_coverage
SET status = 'active', verified_at = '<now>', rejection_reason = '', updated_at = '<now>'
WHERE coverage_key = '<ORG_ID>:<REGION_SLUG>';

If that errors on the last two columns they do not exist yet. Drop them and set status alone, which is the fallback the admin route takes.

5zcql

Clear the three gates on the bid itself zcql

Only needed if a partner is meant to actually place a bid, not just see the cohort. Each of these refuses with its own message, so the message tells you which one.

UPDATE provider_orgs  SET approval_status = 'approved' WHERE org_id  = '<ORG_ID>';
UPDATE provider_users SET role = 'admin'              WHERE user_id = '<USER_ID>';
SELECT config_key, value FROM site_config WHERE config_key = 'bidding_enabled';

Orgs are created pending and nothing self-approves. The first seat in an org is admin and every seat after is viewer, which cannot bid. bidding_enabled absent means on. The standard cohort terms are accepted by the partner in their own console, so provider_terms needs to exist but needs no row from you.

6both

Every later cohort takes a lower number terminal zcql

This is the featured flow. Cohort A is already in the table at <SORT_A>. The new one gets <SORT_A> - 1.

node scripts/cohort.mjs seed <ID_B> --regions "<REGION_B>" --first <DAYS> --sort <SORT_B>

B is now featured, A is position 1, both are live, both are open to bid, and the A row was never touched. Then step 4 again for <REGION_B>: coverage is per region, so a partner covering A's region sees nothing of B's.

To hand the featured slot back, move the newer cohort below the older one rather than moving the older one up, so only one row is ever rewritten:

UPDATE campaigns SET sort_order = <SORT_A + 1> WHERE campaign_id = '<ID_B>';
7both

Verify what both sides will read terminal zcql

Wait 60 seconds first. The catalog is memoized for a minute, and hand-written ZCQL cannot invalidate it the way the admin routes do.

node scripts/cohort.mjs verify <ID>
SELECT campaign_id, region, kind, bidding_open, sort_order FROM campaigns;
SELECT org_id, region, status FROM provider_coverage;

That first result, read top to bottom, is the card order on /dashboard inside each kind bucket, which groups 6f and 6g of scripts/qa-dashboard.mjs assert in a browser. Then, signed in on each side: GET /api/auth/campaigns and GET /api/auth/provider/campaigns. Check live on both. live: false means campaign_members was unreadable and every count is a seed, which looks exactly like a cohort nobody joined.

Two habits worth keeping

Never DELETE a campaign row. There are no foreign keys, so its campaign_members rows survive pointing at nothing. A duplicate key error means the cohort exists: SELECT it and UPDATE what you meant to change.

Let the tool write the literals. ZCQL here has no parameter binding, so cohort.mjs refuses a value containing a quote or a backslash rather than escaping it. A rejected value is a typo you fix. An escaped one is a habit, in a console with full write access.

Part four

What opens a window, and what fails silently

Read this page before you conclude that something is broken. The single most common surprise is a cohort that is in the table, visible to households, and absent from every partner desk.

Coverage: who a cohort reaches

One minute after the INSERT

Consumer, /dashboardPartner, /partner
Appears asa card in "Campaigns near you", badge Sealed bidding a desk row, only where coverage is active
Stagebiddingopen, or closing in the last 24 hours
Can actNo. An auction is not joinableYes, once steps 4 and 5 are done
Refresheson its own, every 15 seconds while the calendar fits in 36 hours never. The console fetches once at boot, so reload it after any ZCQL write

The first row you ever insert hides the other six

An empty campaigns table falls back to the six-region code catalog. A populated one is the truth. So the moment your first cohort lands, the six demo regions disappear from both dashboards. Insert every region you want visible, or expect a one-card site.

What you seeWhat it is
Nothing changed on either dashboardThe 60 second catalog memo. Wait, then reload.

The featured card has no join buttonIt is an auction. Auctions are never joinable.

Desk reads Announced, no bid button bidding_opens_at is still ahead, so bidding_open was written false. Use a smaller <DAYS>, or cohort.mjs bidding <ID> --on.
